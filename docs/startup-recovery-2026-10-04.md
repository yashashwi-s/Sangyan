# Bounded startup recovery — 4 October 2026

The previous published source reached readiness in zero of three changing-network runs. A failed JavaScript module dependency can remain failed for that document, so simply importing the same module again is insufficient. The new bootstrap is included in the initial HTML with an exact CSP hash. It automatically attempts recovery only before the app's ready mark, before a form exists, and while the original language route remains unchanged. The native language links and retry link remain available without JavaScript.

The same-origin public `/main.js` reachability probe has an eight-second timeout. Recovery permits at most two attempts across reloads, recorded only as the public path/counter in session storage, with two/four-second delays. Offline recovery waits for an online event for at most 30 seconds. Storage denial or malformed counters leave manual retry available. Ready screens, entered forms and changed routes are never reloaded. Locale fetches retry transient failures at most twice within their existing 20-second deadline, preserving previously loaded text and private drafts; malformed or missing dictionaries fail directly. Locale switching never triggers this document reload.

The first intermediate experiment recovered but briefly navigated to a Chrome error page while connectivity was still down. Its evidence is preserved separately in `audits/2026-10-04-recovery-lab`. The final reachability-probe experiment, source manifest `58ce04b907a1250a677b2b88f01ce13b7e075284228c7224d4074b5e42498236`, reached readiness in **three of three** changing-network runs. Each used exactly one automatic reload and had **zero Chrome error-page navigations**. Time from the original navigation to readiness was **14.718–14.772 seconds**. Connectivity was interrupted at three seconds and restored at six seconds, with bandwidth/latency phases retained in the raw network log.

The same experiment's three steady runs reached readiness in 5.573–5.674 seconds; its three fresh recovered runs reached readiness in 3.819–3.861 seconds. None of the nine runs requested an MP3. All had no Lighthouse runtime errors or reported warnings. Measurements are navigation-only Chrome lab evidence: 360×800, 8× host CPU slowdown and a 64 MiB V8 old-space setting, not a physical 2 GB phone test. Readiness times after a reload in Lighthouse are relative to the latest navigation, so the reported outage times above are recalculated from the first main-frame navigation trace timestamp. [Compact recovery evidence](audits/2026-10-04-recovery-probe-lab/recovery-evidence.json) and raw traces/network logs retain the distinction.

A longer outage, an initial HTML failure or unavailable storage can still require native manual retry. No guarantee of recovery from every failure is claimed.
